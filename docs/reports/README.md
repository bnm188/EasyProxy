# 开发报告制度（docs/reports/）

本目录存放 EasyProxy 的**每次工作**独立报告。这是项目的长期制度，所有后续开发、修复、测试、编译、审计都必须遵守。

> 编号基线：**自 0.8.13 起从 `001` 重新开始计数**。此前版本（0.8.12 及以下）的过程报告已按要求整体清除，不再保留。

## 1. 编号与命名

- 文件名：`NNN-YYYY-MM-DD-slug.md`
- `NNN` 为三位连续编号，当前从 `001` 开始，**只增不减、不复用、不覆盖**
- `slug` 用英文小写短横线，3~6 个词，描述本次任务
- 一次任务 = 一份报告。同一任务的后续修补也要新编号

## 2. 报告必填内容（缺一项即视为报告不合格）

1. 本次任务名称与目标
2. 本次修改的文件及路径
3. 每个文件修改的具体内容
4. 新增了哪些功能
5. 哪些功能还没有实现
6. 删除了哪些文件及删除理由
7. 执行了哪些测试
8. 每项测试的实际结果
9. 编译是否成功
10. 生成了哪些 IPK / 内核包 / 其他产物
11. GitHub Commit SHA（本次代码提交，报告自身提交单独说明）
12. 本次遗留问题
13. 下一步计划

报告模板见第 5 节，复制后填写。

## 3. 真实性规则（硬约束）

- **没有执行测试，不得写“测试通过”**；没跑就写“本次未执行测试”，并说明原因
- **没有真实运行，不得写“功能已可用”**；跑过沙箱写“沙箱验证”，真机跑过才写“真机验证”
- **没有生成安装包，不得写“安装包已交付”**；只有构建成功且产物可在 Release/Artifacts 取到，才能写“已产出”
- **测试失败必须如实记录**：失败项、失败输出、退出码都留在报告里，禁止只保留成功结果
- **本次没有改代码也要出报告**：记录检查范围、检查结论、为什么没改；但**不得伪造代码提交**
- 报告里出现的行号、文件名、命令输出、SHA、字节数，必须来自本次实测或本次 API 返回
- 易变数据（如 Release 资产哈希）不在报告里固化，改为写“抓取时间 + 当时 `SHA256SUMS` 结果”

## 4. 提交顺序（必须遵守）

1. 先提交代码/配置/文档变更，拿到该提交的 SHA
2. 再提交本次报告，报告第 11 项写第 1 步的 SHA
3. 报告提交本身在报告里注明“报告提交 SHA 见 GitHub 提交历史”
